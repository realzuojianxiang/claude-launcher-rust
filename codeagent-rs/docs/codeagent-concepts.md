## 1. 什么把一个聊天机器人变成 agent

一个普通的 LLM 聊天:你问 → 它答。它只能用它训练时的知识回答,碰不到「此刻」「你的机器上」「那个文件里」的东西。它是张嘴,没手。

**agent 的定义性特征是:它能在回答之前,先对环境做点什么、再根据做的结果来回答。**

- 你的问题: `src/main.rs 里现在用了哪几个第三方 crate?`
- 聊天机器人: 凭记忆瞎猜(大概率过时/错)。
- agent: 先调一个「读文件」工具把 `Cargo.toml` 内容读出来 → 看清楚 `[dependencies]` 段 → 再回答你。

差别不在「模型更聪明」,而在**模型多了一条「先动手、看结果、再说话」的回路**。这条回路就是下面要讲的 ReAct 循环。

一句话:**agent = LLM + 工具 + 循环**。三者缺一就只是聊天机器人。

## 2. 对话天生是不够的:模型自己拿不到信息

理解 agent 为什么要工具,先认清一个反直觉的事实:**你发给模型的 `messages`,就是它全部的世界。** 它看不到你的硬盘、看不到现在的网络时间、看不到它上一句说了啥(除非你把历史也塞进 messages)。它的认知边界 = 你给它的那段 text。

这意味着:

- 你问 `Agent.rs 现在长啥样?`,模型如果真知道,那一定是因为**你(或某个工具)把 Agent.rs 的内容塞进了 messages**。
- 模型不会「自己去文件系统找」。它会做的是:**输出一条指令说「我想调 read_file 工具读 src/lib.rs」**,然后等待。等待的是**你的程序**去真正读文件、把内容塞回 messages、再唤醒它。

所以 agent 的本质不是模型变强了,而是**模型 + 你的程序组成了一条闭环**:模型决定做什么,你的程序去做,做的结果回灌给模型。

模型类比你大脑(出主意),工具类比你手脚(干活),你的程序类比神经系统(把两边连起来,维持循环)。

## 3. 工具调用:让模型获得「手」

模型怎么「表达它想用工具」?这就是 **tool use / function calling** 协议。主流模型提供商(OpenAI、Anthropic、DeepSeek、各家 NIM)都支持一个类似结构:

### 3.1 你先告诉模型有哪些工具

你在发请求时,除了 `messages`,额外带一个 `tools` 字段,描述每个工具的名字、干什么、要什么参数。这是一份**给模型看的「菜单」**:

```json
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "read_file",
        "description": "读取本地文件内容。",
        "parameters": {
          "type": "object",
          "properties": {
            "path": { "type": "string", "description": "文件的绝对或相对路径" }
          },
          "required": ["path"]
        }
      }
    }
  ]
}
```

`description` 极其重要——模型就靠它判断「这个工具适不适合当前任务」。写得糙,模型就乱用或不用。这是 agent 工程里最容易被低估的一处「写 prompt」。

### 3.2 模型决定用工具时,它不回文字,回一条 tool_call

模型如果觉得现在该用 `read_file`,它会在回复里**不带正常 content 文字,而是带一个 `tool_calls` 字段**:

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "tool_calls": [
        {
          "id": "call_abc123",
          "type": "function",
          "function": {
            "name": "read_file",
            "arguments": "{\"path\": \"src/lib.rs\"}"
          }
        }
      ]
    }
  }]
}
```

注意三点:
- `arguments` 是**字符串形式的 JSON**,不是对象。这是 OpenAI 协议的一个反直觉点,新手常在这里踩坑(要 `serde_json::from_str` 解一层)。
- **`id`(`call_abc123`)**是给工具结果回灌时配对用的——模型一次可能调好几个工具,得靠 id 知道哪个结果对哪次调用。
- 模型这次**没给你最终答案**,它在等工具结果。

### 3.3 你的程序执行工具,把结果「回灌」

你收到 tool_call,真的去 `std::fs::read_to_string("src/lib.rs")`,拿到内容。然后你要把它包成一条**`role: "tool"` 的消息**,连同它对应的 id,追加进 messages:

```json
{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "文件 src/lib.rs 的真实内容 ...\nmod config;\n..."
}
```

### 3.4 再调一次模型——让它看到工具结果说话

带着这份新的 messages 再发一次请求。这次模型有了文件内容,它就能回正常 content 了(也可能它还想再调别的工具——见下一节)。

**核心动作回顾:发请求带 tools → 收 tool_call → 执行 → 回灌 role:tool → 再发请求。** 这五步是 tool use 协议的全部机械动作。剩下的问题是:不止一个工具、不止一轮怎么办——那是下一节。

## 4. ReAct 循环:agent 的心跳

「ReAct」= **Reason + Act**:模型推理(Reason)决定要不要行动(Act = 调工具),行动结果反哺推理,推理再决定下一步。round and round,直到模型觉得够了、回纯文字不用工具为止。

一个完整的 agent loop 大致长这样(伪代码):

```rust
let mut messages = vec![system_prompt, user_input];
loop {
    let reply = call_model(&messages, &tools).await?;  // 一轮

    match reply.tool_calls {
        Some(calls) => {
            // 模型想动手 —— 把 assistant 这条(含 tool_calls)也压进历史
            messages.push(assistant_message_with(&calls));
            for call in calls {
                // 真正执行工具
                let result = dispatch(&call).await;
                // 把结果以 role:"tool" 回灌,带 tool_call_id 配对
                messages.push(tool_result_message(&call.id, result));
            }
            // 不 return,回到 loop 顶 —— 模型会看到这些 tool 结果,继续
        }
        None => {
            // 模型回纯文字、不再用工具 —— 这一轮任务结束
            println!("{}", reply.content);
            break;
        }
    }
}
```

四个容易想岔的点:

1. **「assistant 那条含 tool_calls 的消息也要进历史」**。模型回头要能看到「我刚才调过 read_file」才有连贯性。漏了这一步,模型会原地打转,重复要求同一工具。
2. **结束条件是「模型自己不用工具了」**,不是外部硬截断。模型决定停,agent 就停。这就是 agent 的「自主性」来源——也是它有时会跑飞的原因(P4 权限审批就是为了给这自主性加刹车)。
3. **一个 message 里可能有多个 tool_calls**。模型可以一次要读三个文件,你得 all 执行、all 回灌。
4. **每多调一轮工具 = 多花一次模型调用 = 多花钱 + 多耗 context**。这是 agent 工程的内在成本(P6 上下文管理的原因)。一个 agent 不是循环越多越好,而是「用最少的循环把事办了」越好。

ReAct 循环就是 agent 的心跳。心跳稳不稳,全看 3.1 那个 tools 描述清不清晰、3.3 回灌的工具结果信不信得过——这就接到下一节。

## 5. 工具输出怎么写,决定 agent 能不能自我纠正

工具调完拿到的 raw 结果,不一定直接回灌给模型——**回灌什么形态,决定模型下一步想得多清楚**。

比如 `read_file` 读一个不存在的文件,工具内部报错 `FileNotFound`,你有两种回灌方式:

**甲(糙)**: `content: "执行失败"`  
**乙(糙)**: `content: "error: \"FileNotFound\""`

甲让模型完全摸不着头脑,大概率乱试。乙好一些但模型不一定知道「FileNotFound」意味着什么。

**丙(清楚)**: `content: "错误:路径 'src/lib.rs' 不存在。可能原因:相对路径基准是当前工作目录,或文件名拼错。建议先列目录确认。"`

丙既讲了发生了什么,又给了模型下一步的可操作暗示。这才是**面向「下一个消费者是 LLM」来写的错误信息**——agent 工程的关键手艺。

工具结果本质上是给模型打的 prompt。好的工具输出让模型少绕弯;糙的输出让模型在循环里空转(调错文件 → 收到 "失败" → 再调同样错的文件 → 再 "失败" → 死循环)。这也是 P2 多轮 loop 最真实的工程挑战:不是循环写不出来,是**循环容易停不下来**。

所以我们项目里做 P3 扩工具集时,每加一个工具,真正花心思的不是 `execute()` 函数,是它的 `description` + 它回灌的 `content` 格式——这才是决定 agent 聪不聪明的杠杆点。

## 6. 上下文:会话越长,记忆越贵

模型每次调用,把你给它的全部 `messages` 都吃进 token 数里。会话进行下去,messages 越来越长(用户原始问题 + 每轮 assistant 回复 + 每个 tool_call + 每个 tool 结果……),到某个点会撞天花板(provider 的最大 context)。

更深一层的矛盾:**messages 里早期内容往往没必要全留**。比如第 1 轮模型调 `read_file("Cargo.toml")` 拿到的 200 行内容,到第 10 轮还在 messages 里占着 token,但它对第 10 轮的任务很可能已经无关紧要。

所以成熟的 agent 都有「上下文管理」一环,常见手法:

- **滑窗**:只保留最近 N 条消息,老的丢掉。简单粗暴,丢得太狠会忘任务。
- **摘要压缩**:把老对话(特别是长串 tool 结果)用模型压成一句话摘要,替换原样保留。
- **工具结果瘦身**:文件读进来 2000 行,可能只挑模型用得到的段落回灌,其余落盘,只在模型追问时才再贴。

这是个**正交于 ReAct 循环**的话题:循环管「下一步做什么」,上下文管理管「带多少历史进下一步」。一个 agent 撑不死长任务,十有八九是上下文炸了而不是循环写错。这一节对到我们项目的 P6。

## 7. 多 provider:agent 不绑死某个模型

很多人把 agent 和某一家模型绑死,但 agent 的逻辑(provider 之外那部分)其实是**与模型无关**的:ReAct 循环、tool use 协议、上下文管理,换哪家都一样。

这有两个推论:

1. **值得把「调谁」抽成配置**,代码只认抽象的「给 provider 发请求」。我们家 codeagent 的 P0.5 就是干这件事:`base_url`/`model`/`api_key_env` 进 TOML,换 DeepSeek、NVIDIA NIM、OpenAI、本地 ollama 改配置不改循环。
2. **不同模型的 tool use 实现有微妙差异**。OpenAI 协议是事实标准,但各家对 `tool_choice`、并发 tool_calls、arguments 字段解析有不一致处。所以我们 P1 开头会先发个**最小探针请求**把原始返回打印出来再写解析——别空猜,实测最快。

   > 实锤见 [`codeagent-journey.md` §3.2](./codeagent-journey.md):2026-08-06 同一段 read_file tool 在 DeepSeek 和 NVIDIA NIM 上各探一次,两家就在 `index`(有/无)、`content`(空串/null)、`reasoning_content`(英文/中文)三处实实在在分了岔。照一家写死,在另一家首跑就炸——这就是「实测最快」的活证据。

抽配置不只是「好用」的工程整洁,它是 agent 能**跨模型长存**的前提——今天最强的模型明年就不强了,你的 agent 不该随它一起过时。

## 7.5 做 agent 不用 LangChain 吗?

刚开做的人几乎都会问这一句——一搜「怎么做 agent」就撞上 LangChain,名声大到像「做 agent = 用 LangChain」。但当你问的是「**自己做** agent」而不是「凑个 LLM demo」,这就该往「该不该用」想,不是「谁最著名用谁」。

**答:学习场景里,我们不裸写则学不到东西,所以本项目坚持裸写。**

理由四条,从软到硬:

1. **目标是理解内核,不是出 demo**。我们越是「一步一步、从简单到复杂迭代」地学,就越要看得清 tool_call 怎么解析、`id` 怎么配对、循环在哪终止。`Agent(verbose=True)` 跑是跑了,但内核全藏黑盒里——我们刚好走到了细节里,框架就是要你跳过这些细节。**学习时,框架与目标为敌。**

2. **ReAct loop 本身极小**。§4 那段伪代码翻过来看——完整的一轮 loop(发请求→看 tool_calls→执行→回灌→再发)**核心就 20 来行代码**。用框架,你为「省 20 行裸写」去扛几千行黑盒对象的认知负担。框架的省事值,只在循环是「噪音」时才成立;对你是核心,框架就反向加码。

3. **黑盒出错时抓瞎**。agent 的真实日常是 debug:模型为什么调那个工具、为什么重复调、为什么死循环、为什么 `arguments` 炸了。框架把循环藏起来,既看不见模型实际收发了什么,也不敢动框架内部——只能去搜。我们为定位一个 `builder error` 花了整轮,那种**对底层通透**的能力才是 agent 工程的命根子。用框架,下一次报错就是「框架哪层抛的」。

4. **抽象层级错位**。LangChain 把 ReAct 循环、prompt 模板、memory、tool 全塞进一套大而全的抽象,导致「我就想改个 prompt 写法」都得先懂它整套 Runnable 协议。好抽象应是**深模块**(接口窄、实现深);它反着来:**接口宽(要先懂一堆概念才能用)、实现浅(藏不住底层,出 bug 还得下去看)**。这就是它「上手容易、生产难用」口碑的根因。本项目从一开始就把界划清:`Tool` trait 窄接口 + 薄 agent loop——这是我们要建的形态。

**LangChain 什么时候才真值得用**:做产品原型快速验证、不在乎黑不黑只要快出 demo;或只想拿 LLM 干个体力活不打算深入。这俩前提,本学习项目一个都不沾,所以裸写。

> 一句话原则:**框架替你跳过的,正是你要学的**。造自己的工具时,跳过的就是欠的债。

## 8. 从「能用」到「像 Claude Code」之间还差什么

讲到这里,你已经具备造一个「能调一个工具、转一次循环」的最小 agent 的全部概念。但 Claude Code 这种你每天在用的东西,还多出了:

| 它多了什么 | 为什么需要 | 对应我们哪一关 |
|---|---|---|
| 一堆工具(read/write/grep/glob/bash/edit) | agent 的「手」不全就办不了事 | P3 |
| 工具结果格式被精心打磨过 | 模型瞎用工具多半是结果长得让模型乱 | 全程,尤其 P3 |
| 危险动作前问你一声(write/bash) | 给模型的自主性加刹车 | P4 |
| 流式输出 + Ctrl-C | 否则长任务像卡死 | P5 |
| 上下文压缩 | 长任务不炸 context | P6 |
| 会话保存/恢复 | 断点续做 | P7 |
| MCP(让 agent 接第三方工具)、subagent(分派子任务) | 从单兵到能在真实代码库干活 | P8 |

所以「像 Claude Code」不是一道技术难关,而是**几十处像第 5 节那样的心智**:description 写法、错误回灌形态、循环终止策略……每处都不难,但叠起来才是那个每天被你使用的工具。

这也是为什么这份教程坚持「概念 + 做法」不分家:造美的 agent 不靠奇技,靠每一步把「下一轮模型会怎么理解」想清楚。
